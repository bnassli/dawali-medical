# Architecture Decisions
ADR-001: Internal Patient UUID independent from iCare number.
ADR-002: SonoSoft is reference only; new clean data model.
ADR-003: Preserve SonoSoft-style UX/order where practical.
ADR-004: Reports remain editable DOCX.
ADR-005: Inventory is a separate future module.
ADR-006: Medical files stored outside PostgreSQL in private object storage.
ADR-007: Modular monolith for V1.
ADR-008: Use append/version semantics for historical clinical artifacts.
ADR-009: Risk-based testing to reduce delivery time while protecting critical workflows.

## Sprint 1 stack decisions

ADR-010: Next.js (App Router) + TypeScript strict (`strict: true`,
`noUncheckedIndexedAccess: true`) as the application framework. ESLint via
`eslint-config-next`, with `@typescript-eslint/no-explicit-any` forced to
`error`. Plain CSS (no CSS framework) for V1 UI — functional over styled,
consistent with "keep it plain and functional."

ADR-011: Drizzle ORM + `pg` (node-postgres) as the data layer. Schema lives
in `src/db/schema/*.ts`; SQL migrations are generated by `drizzle-kit
generate` into `drizzle/*.sql` and committed to source control (never
hand-edited except deliberate `--custom` migrations such as the audit
append-only trigger). A single migrator (`src/db/migrator.ts`, driven by
`npm run db:migrate`) applies them with `drizzle-orm`'s own migration
runner, which tracks applied migrations in the database itself
(`drizzle.__drizzle_migrations`) so re-running is a no-op.

ADR-012: Custom DB-backed sessions rather than a third-party auth library,
because the domain needs tight, auditable control over session lifecycle
(revocation, expiry, "inactive user can't log in") and Sprint 1 has no
requirement for OAuth/SSO. A random 32-byte token is stored client-side in
an httpOnly, `SameSite=Lax`, `Secure`-in-production cookie; only the
SHA-256 hash of the token is persisted server-side (`sessions.token_hash`),
so a leaked database row alone cannot be replayed as a valid cookie.
Passwords are hashed with Argon2id (`@node-rs/argon2`). Login failures
always return the same generic message and are audited without ever
logging the submitted password.

ADR-013: `audit_logs` is enforced append-only at the database level via a
`BEFORE UPDATE OR DELETE` trigger (see
`drizzle/0001_audit_logs_append_only.sql`), not just by application
convention. This guarantees the audit trail survives even a future
application bug or an ad-hoc script run directly against the database.
Rollback for this migration only drops the trigger/function — it never
deletes or rewrites existing audit rows.

ADR-014: RBAC is modeled as real database rows (`roles`, `permissions`,
`user_roles`, `role_permissions`) seeded idempotently from constants in
`src/modules/permissions/constants.ts`, rather than hard-coded role checks
scattered through the code. This is a system access-control concern, not
one of the "configurable clinical dropdown options" that CLAUDE.md rule
#10 requires to stay data-driven for clinicians — that rule governs future
clinical field option lists (Sprint 2+), not the fixed set of application
roles.

ADR-015: Every module service function takes an explicit `ActorContext`
(`{ userId, displayName, permissions, ip, userAgent }`) and an explicit
`db`/transaction handle, rather than reading the current user from request
globals. This keeps services unit/integration-testable without an HTTP
layer, and is what `test/helpers.ts` relies on to build real actors from
seeded roles for the Sprint 1 test suite.

ADR-016: `npm run db:validate` applies the real committed migrations to a
disposable database (either `TEST_DATABASE_URL` or a throwaway
`embedded-postgres` instance), asserts the expected tables exist, and runs
`drizzle-kit generate` against a scratch copy of `drizzle/` to detect
schema drift (i.e. `schema.ts` changed without a corresponding committed
migration). The Vitest suite's global setup uses the same
migrate-from-scratch path, so every test run also re-validates every
committed migration file.

ADR-017 (known environment limitation, not a design decision): real
PostgreSQL refuses to start under a Windows account that holds the
built-in Administrator group in its process token (`pgwin32_is_admin()`),
which is how the Sprint 1 development sandbox's shell is configured. This
blocks `embedded-postgres` specifically in that sandbox; it does not
affect Linux CI runners (`.github/workflows/ci.yml` uses a real `postgres`
service container instead) or a Windows dev machine running as a standard
user. See README.md "Known limitations" for details and workarounds.
